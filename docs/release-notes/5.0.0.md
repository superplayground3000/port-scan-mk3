# 5.0.0 Release Notes — Bounded Resources and Operator Control

## Summary

Version 5.0.0 puts a limit on every large input. Command-line flags control the
limits for CIDR files, port files, snapshots, target expansion, and pressure
responses.

This release corrects an authorization error in rich input. A `decision=deny` row
can no longer reach an ICMP or TCP probe.

This release returns terminal control to the operator. Ctrl+C now cancels an
interactive scan.

This release corrects three flags that did not do what their names promise.
`-quiet` no longer hides error output. `-progress-interval` now sets the progress
cadence. `-output-flush-results` is new and controls the output batch size.

This release corrects two pressure-control errors. A scan stopped by the pressure
API now exits with code `1`. Non-finite pressure values are now rejected.

This release makes `cidr-compare` stop at the first invalid nonblank CSV record.

This release applies the optional port on each basic CSV row.

This release changes the public Go interface for library callers. Read
[Breaking Go API changes](#breaking-go-api-changes) before you upgrade a Go
application.

CAUTION: Read [Breaking CLI behavior](#breaking-cli-behavior) before you upgrade
an automated pipeline. Several commands now exit with code `1` for input that
version 4.0.0 accepted.

## Breaking CLI behavior

Each item below changes the result of a command that worked in version 4.0.0.

### `-quiet` no longer hides error output

- In version 4.0.0, `-quiet` suppressed every log line except pressure events.
  An operator lost the fatal worker panic and the local-resource warning.
- `-quiet` now suppresses only the periodic progress line and the
  `scan_progress` event.
- `-log-level` is the single owner of log verbosity.
- **Mitigation:** for a silent run, use `-quiet -log-level error`.
- A JSON consumer that reads `scan_progress` must not use `-quiet`. One emitter
  writes the progress line and the event together.

### `-progress-interval` now sets the cadence

- In version 4.0.0, the `scan` parser accepted the flag and discarded the value.
  The cadence was always the built-in `100`.
- `scan` now uses the value. `pre-ping` and `generate-buckets` always used it.
- The default stays `100`. An operator who never set the flag sees the same
  output.
- **Mitigation:** if the new cadence prints too many lines, set
  `-progress-interval` to the previous built-in value of `100`.
- The cadence counts written results. `-output-flush-results` therefore bounds
  how often a progress line can appear.

### `cidr-compare` stops at the first invalid record

- The four parser paths now reject a nonblank record that has too few fields or
  an invalid CIDR.
- An input error produces exit code `1` and empty stdout.
- Version 4.0.0 skipped some of these records. It can report a false result.
- The diagnostic prints the input path without quotation marks. A Windows path
  keeps its single backslashes.
- **Mitigation:** correct the input record that the diagnostic names. To accept
  the old result, use version 4.0.0.

### A rich deny row produces no probe

- A `decision=deny` row produced ICMP and TCP probes in version 4.0.0.
- The rule now applies before ICMP, bucket generation, resume rebuild, and TCP
  dispatch.
- A deny row overrides an accept row with the same normalized `execution_key`.
- A deny-only input writes an empty snapshot and header-only result files.
- A deny-only scan reports zero tasks and exits with code `0`.
- `scan` rejects an unmarked snapshot with rich deny input before TCP dispatch.
- **Mitigation:** if this snapshot error occurs, run `generate-buckets` again.

### A snapshot with trailing content is invalid

- The legacy snapshot decoder accepted content after the JSON array. A file such
  as `[] {}` loaded as a valid snapshot.
- The decoder now requires end of input after the array.
- Version 4.0.0 rejected the same file. This release restores that behavior.
- **Mitigation:** if the loader reports trailing content, run `generate-buckets`
  again to write a new snapshot.

### An input larger than a default limit is rejected

- Version 4.0.0 read a file of any size. The new defaults reject a larger input
  before the command opens a network socket.
- The defaults are in [Input, snapshot, and pressure limits](#input-snapshot-and-pressure-limits).
- **Mitigation:** raise the related flag, or set it to `0` to disable that limit.

## Interactive cancellation correction

- `scan` starts a raw-mode keyboard loop on an interactive run. Raw mode cleared
  the terminal `ISIG` flag, so the terminal stopped making `SIGINT`.
- Ctrl+C arrived as the byte `0x03`, and the keyboard reader discarded it. The
  scan continued.
- The keyboard loop now keeps `ISIG` set. Ctrl+C cancels the scan.
- The space key keeps its speed-control function.
- A Linux test measured exit code `130` within 0.1 seconds of the Ctrl+C byte,
  under a real controlling pty.

In version 4.0.0, the only way to stop an interactive scan was `kill` from a
different terminal.

### Ctrl+\ is live again, and it is not graceful

`ISIG` is one terminal flag for three signal characters. It controls INTR
(Ctrl+C), QUIT (Ctrl+\), and SUSP (Ctrl+Z) together.

`port-scan` traps `os.Interrupt` alone. It does not trap `SIGQUIT`.

CAUTION: Do not press Ctrl+\ during a scan. The process dumps core and stops at
once. It writes no resume snapshot, and the console can stay in raw mode.

If the console stays in raw mode, run `reset` to restore it. Ctrl+Z is safe,
because a shell with job control restores the terminal settings of the job.

This release accepts the trade rather than corrects it. Ctrl+\ did nothing in
version 4.0.0, because the keyboard loop discarded the byte. Read
[`../interrupt-handling.md`](../interrupt-handling.md) for the complete signal
table.

## Target expansion limits

- `-target-count-limit` sets the candidate limit. The default is `10000000`.
- `-target-memory-limit-gb` sets the memory budget in decimal GB. The default is
  `16`.
- The estimate is `1000000000 + candidate count * 1500` bytes.
- A value of `0` disables its limit. A negative value is an error.
- All commands stop before network probes and output creation when a limit fails.
- `validate` calculates the estimate without target enumeration.
- `generate-buckets` stores the effective limits and candidate count.
- `scan` counts only incomplete chunks and uses stored limits by default.

CAUTION: If both limits are `0`, target expansion has no hidden limit. The
process can stop when the host or operating system cannot supply more resources.

## Input, snapshot, and pressure limits

This release adds ten flags. Each flag has its own default, and a value of `0`
disables only that limit.

| Flag | Default | Limit |
|---|---|---|
| `-cidr-input-size-limit-gb` | `1` | CIDR input size in decimal GB |
| `-cidr-input-record-limit` | `10000000` | CIDR data records |
| `-port-input-size-limit-mb` | `1` | Port input size in decimal MB |
| `-port-input-record-limit` | `65535` | Nonblank port records |
| `-snapshot-size-limit-gb` | `2` | Snapshot load and save size in decimal GB |
| `-snapshot-chunk-limit` | `10000000` | Snapshot chunks |
| `-snapshot-port-entry-limit` | `10000000` | Snapshot port entries |
| `-snapshot-unreachable-ip-limit` | `10000000` | Snapshot unreachable IPs |
| `-pressure-response-size-limit-mb` | `1` | Size of each pressure response in decimal MB |
| `-pressure-response-entry-limit` | `10000` | Entries in each OAuth data array |

Each command accepts the flags for the resources it reads:

- `pre-ping` accepts the two CIDR flags.
- `validate` accepts the CIDR and port flags.
- `generate-buckets` accepts the CIDR, port, and snapshot flags.
- `scan` accepts all ten flags.

Rules that apply to every flag in this table:

- A positive value replaces its default.
- A negative value is an error before file or HTTP adapter work.
- A value of `0` disables only its related limit.
- A failed snapshot replacement keeps the previous file unchanged.

CAUTION: If you disable a limit, the process can exhaust memory and stop.

Go callers can use the `WithResourceLimits` constructors for explicit values. The
existing constructors use the new defaults.

## Batched scan output

`-output-flush-results` sets the result count between output flushes. The default
is `1000`.

- Use `-output-flush-results 1` to flush each probe result.
- Use `-output-flush-results 0` to flush only the final batch.
- Positive values have no fixed maximum.
- Each resumed run uses its current flag value.
- A controlled stop flushes its final batch.
- An output failure rewinds the complete uncommitted batch.
- A resumed scan can duplicate rows from an uncommitted batch.

## Basic row ports

A row port overrides the port file for that row. A blank row port uses all ports
from the port file. If all basic rows contain a port, `-port-file` is optional.

## Pressure control corrections

### A failed pressure API now ends the scan with an error

- Three consecutive pressure API failures stop a scan.
- In version 4.0.0, that scan reported success and exited with code `0`. The
  result loop left the queued pressure error unread.
- The scan now returns the error and exits with code `1`.

CAUTION: Do not trust an exit code of `0` from version 4.0.0 as proof of a
complete run. After a pressure stop, that version writes fewer rows than the
input asks for.

### Non-finite pressure values are rejected

- A successful `pkg/pressure` sample contains only finite values.
- A successful result from `scanapp.PressureSource` contains only finite values.
- `NaN`, infinity, and signed infinity are now errors.
- Finite zero, negative values, and values more than 100 remain valid.
- The first two pressure failures retain the current pressure-control state.

In version 4.0.0, the monitor treated `NaN` as less than the threshold. It can
resume a paused scan and clear the failure streak.

## Breaking Go API changes

- `RunOptions.ProgressInterval` is removed. Set `ProgressInterval` on the scan
  configuration instead. The resolved configuration is the single source of the
  progress cadence, which is what makes the `-progress-interval` flag work.

`scanapp.RunOptions` now exposes `Dial`, `DisableRateLimit`, `TaskObserver`,
`ResumeObserver`, `ResultObserver`, `ProbeTelemetryObserver`,
`SnapshotTelemetryObserver`, `PressureLimit`, `DisableKeyboard`,
`PressureSource`, `ReachabilityChecker`, `OutputFailure`, and `SnapshotFailure`.

## Migration examples

Move the progress cadence from the run options to the configuration:

```go
// Version 4.0.0
cfg, err := config.NewScan(config.ScanValues{ /* ... */ })
if err != nil {
    return err
}
return scanapp.Run(ctx, cfg, stdout, stderr, scanapp.RunOptions{
    ProgressInterval: 500,
})
```

```go
// Version 5.0.0
cfg, err := config.NewScan(config.ScanValues{
    // ... the same values ...
    ProgressInterval: 500,
})
if err != nil {
    return err
}
return scanapp.Run(ctx, cfg, stdout, stderr, scanapp.RunOptions{})
```

For explicit resource limits, use the `WithResourceLimits` constructor of the
package that owns the limit:

```go
limits := state.SnapshotLimits{
    MaxBytes:          4_000_000_000,
    MaxChunks:         state.DefaultSnapshotChunkLimit,
    MaxPortEntries:    state.DefaultSnapshotPortEntryLimit,
    MaxUnreachableIPs: state.DefaultSnapshotUnreachableIPLimit,
}
snap, err := state.LoadSnapshotWithLimits(path, limits)
```

## Performance evidence

This release adds a private, cross-platform large-data harness for `port-scan`.
The harness uses production parsing, bucket, resume, scan, and writer paths.

Run `make verify-performance` for the complete native Linux matrix. Linux and
Windows CI run bounded 100,000-record and 100 MB smoke cases.

Each report includes one cold run and a five-run steady-state median. The report
also includes fixture manifests, correctness checks, metrics, thresholds, and
hardware details.

The harness reports separate snapshot load and save results. The save result
includes serialization, write, sync, close, and replacement. The harness performs
the correctness reload after the measured save operation.

The CIDR file loader no longer retains decoded CSV rows beside domain records. It
counts rows first and then converts each row directly to a domain record. The
loader returns an error if the file changes its record count during these passes.

The complete matrix records the scale budgets of issue 151. Read
[`../performance-harness.md`](../performance-harness.md) for commands and report
fields.

NOTE: Two committed-memory budgets are hardware-qualified. They run only under
`make verify-performance`, because an absolute byte ceiling measures the host as
much as the code.

## Compatibility

- Most existing CLI invocations do not need migration. Read
  [Breaking CLI behavior](#breaking-cli-behavior) for the exceptions.
- Current snapshots remain readable. Compatible legacy snapshots remain readable.
- If basic input contains a row port, an unversioned snapshot is not compatible.
- If this snapshot error occurs, run `generate-buckets` again before `scan`.
- Legacy basic snapshots without row ports remain readable.
- Rich snapshots keep their target set and resume behavior.
- New snapshots record `rich_deny_excluded=true`.
- New snapshots record target expansion limits and the pre-filter candidate count.
- New snapshots include `target_expansion` and `target_semantics_version`. Basic
  snapshots also record the port-file fallback.
- The CSV and unreachable-result schemas do not change.
- `validate` still accepts and verifies the complete legacy flag set.

## Cancellation safety

This section describes what happens after cancellation starts. Read
[Interactive cancellation correction](#interactive-cancellation-correction) for
the reason Ctrl+C did not start it in version 4.0.0.

- The first Ctrl+C or Windows Ctrl+Break starts graceful cancellation.
- Input parsing, runtime rebuild, dispatch waits, and queue sends stop.
- Queued probes do not start. Started probes finish with their original timeout.
- The command writes late in-flight results before snapshot persistence.
- The snapshot rewinds each chunk to its lowest unwritten task.
- A resumed run can repeat a row. It cannot skip an unwritten task.
- The second Ctrl+C or Ctrl+Break forces exit code `130` immediately.
- A snapshot-save error returns exit code `1` and reports prior snapshot
  usability.

The second-interrupt escalation and the chunk rewind are new in this release.
Version 4.0.0 canceled on the first interrupt, but it had no forced second exit.

## Rollback and mitigation

CAUTION: Do not roll back a rich workflow that contains deny rows. Version 4.0.0
can scan a rich deny row.

CAUTION: Plan a different stop method before you roll back. Version 4.0.0 cannot
cancel an interactive scan from the terminal that started it.

Version 4.0.0 remains suitable for other CLI rollback cases. Do not reuse a 5.0.0
snapshot after rollback. Create a new snapshot with the rollback version.

A Go application that rolls back must restore its `RunOptions.ProgressInterval`
assignment and remove the field from its scan configuration.

If an application cannot migrate in one change, isolate its version-specific
calls behind a small application-owned adapter. Do not pass partially verified
values to a workflow.
