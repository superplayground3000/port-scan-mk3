# 2.2.0 Release Notes — A Working Version Contract And A Tag-Triggered Windows Release

## Summary

Adds the two things this project shipped without: a way to ask a binary what it
is, and a repeatable path from a git tag to verified Windows assets (issue #70).

Until now the Makefile passed `-X main.version` and `-X main.buildTime` to the
linker on every build, but **no command declared those variables**. `go tool
link -X` writes nothing and says nothing when its target does not exist, so both
stamps had always been silently discarded and there was no way to determine
which commit a binary came from. There was also no release workflow, no archive
or checksum policy, and no test that ran a built artifact.

Nothing about scanning behavior changes in this release.

## Features

- **Every command reports its version.** `port-scan`, `preprocess`,
  `enrich-targets`, `cidr-compare` and `csv-transform` all accept `version`,
  `--version` and `-version` as their first argument and print the release
  version, full commit, build time and toolchain to stdout, exiting `0`. The
  exact format and the per-field policy are documented in the README under
  "Version Contract".

- **The commit is stamped separately from the version.** A build made exactly on
  a tag describes as just `v2.2.0`, which carries no commit at all — the one
  thing a published asset must be traceable to. `LDFLAGS` gained
  `-X main.commit=$(COMMIT)`.

- **Tag-triggered release workflow** (`.github/workflows/release.yml`). Pushing
  a `v*` tag builds all five Windows amd64 EXEs from the tagged source on a
  clean runner, archives them with SHA-256 checksums, verifies the checksum and
  **executes every EXE on a native `windows-latest` runner**, and only then
  publishes the GitHub Release. Assets are always built from source; no binary
  is committed to this repository.

- **Reproducible release archives.** `scripts/package_release.sh` normalizes
  archive entry timestamps to the commit's timestamp and fixes entry order, so
  two packaging runs of one commit produce a byte-identical `.zip`. That is what
  makes the published checksum worth checking. It reuses
  `scripts/verify_dist.sh` (via `make build`) for artifact targeting rather than
  re-implementing it.

- **An artifact smoke test that can fail** (`scripts/smoke_release.sh`). It runs
  every binary and rejects one that reports `dev`, an unknown commit, a
  modified working tree, or a version other than the tag being released. It is
  bash, not PowerShell, so the same script runs on the Linux packaging runner
  and under Git Bash on the Windows runner.

- **Windows install documentation** (README, "Windows Install, Upgrade and
  Rollback"): checksum verification, per-user and machine-wide install
  locations, PATH setup, upgrade with a snapshot backup, and rollback — all in
  PowerShell.

## Policy statements

- **Build time is derived from the commit, never the wall clock**, and
  normalized to UTC. This preserves the byte-for-byte reproducibility guarantee
  from issue #65/#73; the new commit stamp is likewise commit-derived and does
  not disturb it.
- **Dirty builds are marked and refused.** `git describe --dirty` appends
  `-dirty`; the version report then carries an explicit warning line, the
  release workflow refuses to package such a build, and the smoke test refuses
  to pass one.
- **Unstamped builds report `dev` / `unknown`.** A binary from `go build`,
  `go run` or `go test` has no ldflags and says so, rather than inventing a
  version.
- **Docker e2e validates Linux, not Windows.** The e2e suite runs Linux
  containers (constitution V). Windows coverage comes from the native Windows
  CI job and the release workflow's Windows smoke job.
- **Windows ARM64 is out of scope.** Release assets are Windows x64 only.

## Regression protection

`tests/release` builds real binaries with the Makefile's own `LDFLAGS` string —
read out of the Makefile, with sentinels substituted — runs them, and asserts
the sentinels come back out. An in-process test cannot prove this: `go test`
links no `-X` stamps, so a test asserting the `dev` fallback passes just as
happily against a recipe whose stamps go nowhere. That is precisely how the dead
flags survived unnoticed.

The guard was verified by mutation: renaming the `version` variable in one
command makes that binary report `dev` while its commit and build time still
stamp correctly, and the test fails.

## Compatibility

- **No CLI flags changed, removed or renamed.** The version tokens are additive
  and only recognized in first position, so they cannot shadow an existing flag.
  `version` was not previously a valid first argument for any command.
- No output file, schema, or resume-state change. No scanning behavior change.
- `make build` still produces the same directory layout and still runs
  `scripts/verify_dist.sh`; artifacts remain `CGO_ENABLED=0`, `-trimpath`, and
  byte-identical per commit.
- Binaries built before this release report nothing when asked for a version
  (`version` was an unrecognized argument); there is no migration step.
- Rollback: revert the commit. The `LDFLAGS` change is additive, and no on-disk
  format is involved.

## Release tags must be annotated

The workflow fails the release if `git describe` does not report exactly the
pushed tag. Create release tags with `git tag -a v2.2.0 -m "..."`; a lightweight
tag is invisible to `git describe` and would stamp the binaries with a version
that does not match the release they ship in.
