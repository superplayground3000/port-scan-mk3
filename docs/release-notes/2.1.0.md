# 2.1.0 Release Notes

## Summary

Performance release for the `scan -resume` runtime rebuild — the pre-dial phase
that expands a bucket snapshot back into in-memory scan targets. On large resumes
this phase previously dominated wall-clock time (the reported case spent hours in
it before dialing a single port). Two changes make it fast, with **no change to
what gets scanned** for still-to-scan work:

- **Rich execution-key merge is now O(N) instead of O(N²)** (Phase 1): a
  per-group execution-key map replaces the per-insert linear scan, so a segment
  of N targets builds in O(N). Each IP is now parsed once.
- **Resume expands only the still-to-scan work** (Phase 2): completed chunks are
  no longer re-expanded, and incomplete chunks expand only the CSV rows that feed
  them. On the measured fixture (a bucket of 4000 chunks with ~130 still
  incomplete over a 4000-row CSV), the runtime rebuild drops from ~252 ms to
  ~7 ms (~35×) because it expands 130 chunks instead of 4000; on the reported
  real-world bucket — far larger, and previously multiplied by the Phase 1
  quadratic — this is the difference between hours and seconds before dialing.

## Behavior change (call-out)

- **A completed chunk whose CIDR was removed from the input CSV now resumes
  cleanly instead of erroring.** Previously every chunk in the resume snapshot —
  including already-finished ones — was looked up against the current CSV, so a
  fully-scanned chunk whose row was deleted produced
  `resume state references <cidr>, which has no scannable targets…`. Completed
  chunks are now never looked up (they carry no work), so their absence from the
  CSV is harmless. Their finished progress is still preserved verbatim in the
  re-saved snapshot. This is a benign relaxation: a chunk that is already done
  need not remain in the input.

This is the only observable behavior change. Still-to-scan (incomplete) work is
byte-for-byte identical: the same targets, order, ports, and metadata as before,
proven by a differential golden test over the rich-shape matrix.

## Compatibility notes

- **Divergence is still caught loudly.** The `total_count` invariant check is
  retained. If the input CSV changed such that an incomplete segment's rebuilt
  target count no longer matches its saved `total_count` (for example, malformed
  non-disjoint segments where a removed segment had first-claimed a shared
  execution key), `scan` fails with
  `resume state for <cidr> is incompatible with the current target set…` rather
  than silently scanning a diverged set.
- **Snapshot format is unchanged.** The `{chunks, pre_scan_ping}` envelope
  (including the sorted `unreachable_ipv4_u32` blocklist) is byte-identical to
  2.0.0; `pkg/state` needs no reader change. Legacy `[…]` chunk-array snapshots
  still load.
- **Fresh (non-resume) scans are unaffected.** All chunks are incomplete and all
  keys are present, so both optimizations are no-ops on a fresh build.

## Versioning note

Additive performance work plus one benign behavior relaxation → **MINOR** bump
from `2.0.0`. Product version is release-notes-and-git-tag based (the build
stamps `git describe`); tag the release `v2.1.0` at merge.

## Verification

- `make verify` exits `0` (gofmt, `go vet`, build, `go test -race -shuffle=on`,
  and the ≥85% coverage gate).
- Differential golden (`TestBuildRuntime_DifferentialGolden_AllIncomplete`) holds
  the incomplete-work output identical across the refactor; completed-chunk
  handling and the divergence guard are covered by dedicated tests.
- `BenchmarkResumeRebuild/resume_runtime_130_of_4000` demonstrates the drop.
