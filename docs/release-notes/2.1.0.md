# 2.1.0 Release Notes — Speed Up Scan Preparation

## Summary

This release makes `scan -resume` fast and its output durable. On large buckets the
pre-dial "runtime rebuild" (expanding a bucket snapshot back into in-memory scan
targets) previously dominated wall-clock time — the reported case spent hours in it
before dialing a single port — and an interrupt could strand already-scanned rows.
Four themes:

- **Faster rebuild** — the rich execution-key merge is now O(N) instead of O(N²),
  each IP is parsed once, and a resume expands only the still-to-scan work.
- **Durable on Ctrl+C** — rows scanned before a graceful interrupt are on disk at
  the final path, not stranded in a `.tmp`.
- **Resume appends** — `-resume` continues the same output file(s) instead of
  minting a new timestamped pair, and does so crash-consistently.
- **Visible progress** — the previously-silent rebuild phase now logs its progress.

## Performance

- **Rich execution-key merge O(N²) → O(N).** A per-group execution-key map replaces
  the per-insert linear scan, so a `dst_network_segment` of N targets builds in
  O(N). Measured: a `/20` PRECHECK_ALLOW_ALL segment 24.98 ms → 3.17 ms (7.9×), and
  the per-doubling time ratio drops from ~3.5× (quadratic) to ~2.2× (linear).
- **Parse each IP once.** The reachable predicate derives its `uint32` from the
  already-parsed address instead of re-parsing, and group sorts read a precomputed
  key — basic-mode rebuild allocations roughly halve.
- **Resume expands only still-to-scan work.** Completed chunks are no longer
  re-expanded (they get a lightweight runtime, preserved verbatim in the re-saved
  snapshot); incomplete chunks expand only the CSV rows that feed them. On the
  measured fixture (4000 chunks, ~130 incomplete, 4000-row CSV) the rebuild drops
  ~252 ms → ~7 ms (~35×); on the reported real-world bucket — larger, and formerly
  multiplied by the quadratic merge — this is the difference between hours and
  seconds before dialing.

Still-to-scan (incomplete) work is byte-for-byte identical — same targets, order,
ports, and metadata — proven by a differential golden test over the rich-shape
matrix. The `unreachable_ipv4_u32` blocklist was never a bottleneck (sorted
`[]uint32` + binary search) and is unchanged.

## Data integrity: Ctrl+C delivery + resume append

- **Deliver results on Ctrl+C.** `scan` writes rows straight to the final
  `scan_results-<ts>.csv` / `opened_results-<ts>.csv` (no `.tmp` intermediate, no
  rename-on-success), so every row scanned before a graceful cancel (`SIGINT` /
  `context.Canceled`) is already durable. Previously rows went to a `*.csv.tmp`
  promoted only on full success, so an interrupt stranded them.
- **`-resume` appends to the prior output.** The output paths are recorded in the
  resume snapshot (a new optional `output` field). On resume `scan` reopens those
  files in append mode and writes the remaining rows — one continuous file, single
  header, no lost or duplicated rows on the graceful path. A recorded output whose
  directory or file was deleted between runs is recreated (with a header).
- **Append-reopen hardening.** On append-reopen `scan` (a) `MkdirAll`s the output
  directory so a `-resume` whose recorded directory was deleted recreates it
  instead of failing `ENOENT`, and (b) reads the existing first line and requires
  it to equal the canonical `writer.Columns` header, failing loudly on a
  mismatched/foreign/older schema rather than appending under it. It does not count
  or truncate data rows: because result rows may carry rich fields with embedded
  newlines (which `encoding/csv` quotes), a line-based row reconciler is unsafe, and
  the graceful path needs none — see the residual note below.

## Phase-progress logging

The otherwise-silent pre-scan rebuild now emits, in addition to (not replacing) the
existing per-result `scan_progress` / `scan_completion` events: `bucket_parse_start`
(count of incomplete chunks to expand), `bucket_parse_progress` (throttled ticks via
`pkg/progress`, one per incomplete chunk, gated by `-progress-interval`),
`bucket_parse_complete` (chunks parsed, targets generated, elapsed), and
`scan_start` (the transition from preparation to dialing). These go to stderr /
structured logs (constitution VI) and honor `-quiet`.

## Behavior changes (call-outs)

- **A completed chunk whose CIDR was removed from the input CSV now resumes cleanly
  instead of erroring.** Completed chunks are never looked up (they carry no work),
  so their absence from the CSV is harmless; their finished progress is still saved.
- **No more `*.csv.tmp` files for scan/open results.** Tooling that watched for a
  `scan_results-<ts>.csv.tmp` → `.csv` rename should watch the final file directly.
  (The `preping` `unreachable_results` writer is unchanged and still uses `.tmp` +
  rename.)
- A completed fresh (non-resume) run is otherwise identical — a headered
  `scan_results` / `opened_results` pair, just without the `.tmp` intermediate.

## Known limitation (residual)

Durability is exact for the graceful interrupt this feature targets: a `Ctrl+C`
(`SIGINT` / `context.Canceled`) leaves both output files ending at a complete
record with the snapshot cursor matching, so the resumed run appends with no lost
and no duplicated rows.

A **hard crash** (`SIGKILL` / power loss) during a **resumed** run — never a
graceful `Ctrl+C` — is not made crash-consistent: rows written after the last
snapshot checkpoint may be re-scanned and duplicated on the next resume, and if the
crash landed mid-write the file may carry a truncated trailing record that the
append then follows. Recover by de-duplicating / trimming the trailing partial
line. Row-level reconciliation was deliberately not attempted: doing it correctly
requires CSV-record-aware parsing (fields can contain quoted newlines, so a
line-based cut can split a record) plus a write-durability invariant the result
loop does not currently provide — disproportionate to a hard-crash-mid-resume edge,
and worse to ship half-correct. A dedicated, CSV-aware crash-consistency pass can
follow if the hard-crash case proves to matter in practice.

## Compatibility notes

- **Divergence is still caught loudly.** The `total_count` invariant is retained: if
  the input CSV changed so an incomplete segment's rebuilt target count no longer
  matches its saved `total_count`, `scan` fails with `resume state for <cidr> is
  incompatible with the current target set…` rather than scanning a diverged set.
- **Snapshot format is a superset.** The resume envelope gains an optional
  `output: {scan_path, open_path}` field; snapshots written before this release
  (no `output`) still load and mint fresh output paths. Legacy `[…]` chunk-array
  snapshots still load.
- **Output schema unchanged.** `writer.Columns` is byte-for-byte identical — no
  MAJOR bump.
- **No flags added or removed.** Additive performance + data-integrity + logging,
  with two benign behavior relaxations → **MINOR** bump from `2.0.0`. Product
  version is release-notes-and-git-tag based (the build stamps `git describe`); tag
  the release `v2.1.0` at merge.
