# 2.1.1 Release Notes — An Output-Write Failure No Longer Poisons `-resume`

## Summary

Fixes silent data loss when writing the scan output CSV fails mid-run
(issue #51). Previously such a run still saved a resume snapshot, and the next
`-resume` skipped every row that was in flight when the write failed — the exact
loss `-resume` exists to prevent. The run now refuses to save that snapshot and
says so loudly.

No CLI flags, no output schema changes, no migration steps.

## Fixes

- **An output-write failure never leaves a trustworthy-looking resume snapshot.**
  The dispatch cursor (`next_index`) advances when a task is *enqueued*, not when
  its result is written. A write failure breaks that coincidence: results already
  counted in the cursor were never persisted. Resume treats a chunk as finished
  when `next_index >= total_count`, so the snapshot made the scanner skip rows
  that are absent from the output file — including the dispatched-but-unwritten
  tail of a partially-dispatched chunk. The blast radius was roughly
  queued + in-flight + buffered ≈ 3×`-workers` rows.

  Write errors are now tagged at their single point of origin and, when a run
  terminates from one, the resume snapshot is **not** written: the run logs the
  structured event `resume_state_not_saved` (fields: `reason`, `resume_path`,
  `action`) and exits with an error explaining that resume state was
  deliberately not saved, and what the recovery options are.

- **The scanned counter no longer counts rows that were never written.** Results
  drained after the failure — and the failing result itself — used to increment
  the chunk's scanned counter and the completion summary. `total_tasks` in the
  `scan_completion` event now equals the data rows actually present in
  `scan_results-*.csv`.

## Behavior changes (CLI-observable)

- On an **output-write failure only**, `port-scan` exits with a new error of the
  form:

  ```
  resume state was deliberately NOT saved to <path>: writing scan output failed,
  so the saved dispatch cursor would cover rows that never reached the output
  file and the next -resume would skip them silently. The bucket file is
  unchanged, still holding the cursor from before this run, so re-running the
  same scan -resume command covers every target - but the rows this run already
  wrote stay on disk, either appended again to the same outputs or left behind as
  separate partial files, so reconcile BOTH scan_results-*.csv and
  opened_results-*.csv before consuming. For a clean single output, re-run
  generate-buckets and scan into a fresh path:
  scan output write failed: <underlying error>
  ```

  **Recovery.** "Do not resume" is not an available option — `scan` requires
  `-resume <bucket file>` and refuses to run without one. The two real choices
  are the ones the message names, and **neither loses targets**:

  1. Re-run the same command. Every target gets covered. The failed run's rows
     remain, though — appended a second time if the bucket carried recorded
     output paths, or sitting in leftover partial files if it did not. This hits
     **both** result files: `scan_results-*.csv` and `opened_results-*.csv` are
     opened together and leave the same leftover shape. Reconcile both before
     consuming; a glob over either would double-count.
  2. Re-run `generate-buckets` for a fresh bucket file and scan into a new
     output path, for one clean file at the cost of rescanning from zero.

  Losslessness under option 1 is covered by
  `TestRun_AfterDeclinedSaveOnWriteFailure_ReResumeCoversEveryTarget`, which
  fails if a future change makes the recovery drop targets. This follows the
  same preference the 2.1.0 notes record — duplicated-but-recoverable over
  silently-lost.

  and the bucket/resume file on disk is left byte-for-byte unchanged.
- A `scan_completion` summary is now also emitted when the run ends because the
  resume snapshot could not be (or was deliberately not) saved. Previously that
  path returned without a summary.

**Accepted trade-off.** After an output-write failure the operator loses the
run's progress and must restart. That is deliberate: the previous behavior
preserved progress but silently discarded results. Recovering the progress-
preserving property requires rewinding the dispatch cursor to a per-chunk
watermark, which is tracked separately (issue #57) and is **not** in this
release.

## Unchanged

- **Graceful interrupt (Ctrl+C) durability from 2.1.0 is untouched.** A canceled
  run still writes its snapshot with advanced-but-incomplete cursors, still
  records the output paths, and still appends to the same files on `-resume`.
  Pressure-API failures and executor panics likewise keep their existing
  snapshot-saving behavior.
- No row-level or CSV-aware output reconciliation was added; it stays rejected
  for the reason given in 2.1.0 (rich records can contain quoted embedded
  newlines, so line-based reconciliation is unsafe).

## Upgrade / rollback

Drop-in. Rolling back to 2.1.0 restores the previous behavior, including the
silent-skip bug — not recommended.
