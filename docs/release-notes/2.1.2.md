# 2.1.2 Release Notes — A Local Winsock Failure Is No Longer Reported As A Closed Port

## Summary

Fixes silent data corruption in the scan output on Windows (issue #62).
Previously every non-timeout dial error became the status `close`, so a failure
of the **scanning host** — Winsock ephemeral-address exhaustion
(`WSAEADDRNOTAVAIL`), socket buffer exhaustion (`WSAENOBUFS`) or a permission
denial (`WSAEACCES`) — was written to `scan_results-*.csv` exactly as if the
remote port had been probed and found closed. Those rows then flowed into every
downstream consumer that filters on `close` (for example the cleaned-CIDR loader
in `pkg/preprocess`) as confirmed facts about the target.

Dial errors are now classified explicitly, and only a genuine refusal from the
remote end produces `close`.

**Output schema change** (no flags changed, no migration steps): the `status`
column can now contain two additional values. Tooling that treats "not open" as
"closed" should be updated to switch on the exact status.

## Fixes

- **Local resource/permission failures are recorded as `error(local)`, never as
  `close`.** The dial never characterized the target, so the row states exactly
  that. The first occurrence in a run emits an `error`-level log line naming the
  condition; every occurrence carries an `outcome` field in its
  `scan_probe_result` event.

- **Unclassifiable transport errors are recorded as `unknown`.** Host/network
  unreachable and any error carrying no recognizable errno no longer claim the
  port was closed.

- **Classification is structural, never textual.** Matching walks
  `*net.OpError -> *os.SyscallError -> syscall.Errno` (with an `errors.As`
  fallback for other wrappings) and compares errno values. Windows error
  *messages* are localized, so message matching was never an option; Go's
  Windows `syscall` package also exposes almost no `WSAE*` names and its
  Unix-style `E*` constants there are synthetic values above
  `syscall.APPLICATION_ERROR`, so the Winsock codes are matched by their stable
  numeric values (10013, 10024, 10048, 10049, 10054, 10055, 10060, 10061,
  10067).

## Status vocabulary

| Status | Meaning |
|--------|---------|
| `open` | TCP handshake completed |
| `close` | The remote end refused or reset the connection — the only status that asserts the port is closed |
| `close(timeout)` | No answer within the scan timeout |
| `error(local)` | The scanning host failed (address/buffer/handle exhaustion, permission denied). Port state unknown |
| `unknown` | Any other transport error. Port state unknown |

## Failure policy and resume durability

`error(local)` and `unknown` are **indeterminate and non-fatal**: the scan
continues and each affected target still produces exactly one persisted row.
That keeps the invariant `-resume` depends on — the dispatch cursor advances at
enqueue time and is only trustworthy while "dispatched ⇒ persisted" holds
(issue #51) — so resume state stays internally consistent, and no target is ever
advanced as *confirmed closed* on a local failure.

Two alternatives were rejected and are recorded here for reviewability:
treating a local resource failure as fatal for the run (Winsock exhaustion is
transient and load-dependent; aborting would discard a long scan and, under the
issue #51 rule, its resume snapshot), and retrying inside the dial path (adds
unbounded latency to a hot path; explicitly out of scope for issue #62).

## Compatibility

- No CLI flags added, removed or changed.
- `scan_results-*.csv` and `open_results-*.csv` keep their columns; only the
  `status` vocabulary grew. `open_results-*.csv` is unaffected in content (it
  filters on `open`).
- Consumers that computed "closed = not open" will now see `error(local)` and
  `unknown` rows separately. Re-scanning exactly those targets is the intended
  recovery.
- Rollback: revert the commit; no state file, snapshot or on-disk format
  changes are involved.
