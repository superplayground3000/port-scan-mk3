Phase 1 — after-optimization profile
====================================
Companion to profile-before.txt. Same benchmark
(pkg/scanapp/resume_rebuild_bench_test.go), same machine, after:
  1a: rich execution-key merge O(N^2) -> O(N) via per-group map index
  1b: parse each IP once (no 2nd net.ParseIP in the predicate; sorts use a
      precomputed scanTarget.ipU32 instead of net.ParseIP per comparison)

rich /24 (256)               297,739 ->     248,658

Rich merge is now LINEAR. Per host-count doubling:
  before (quadratic): /22->/21 x3.14, /21->/20 x3.72
  after  (linear):    /22->/21 x2.16, /21->/20 x2.29

Flat top is now dominated by GC (runtime.scanObject 35.77%) from ExpandIPSelectors
materializing IP strings, plus the basic build itself. That is problem A: the
whole input CSV is still expanded on every resume. Phase 2 (expand only pending
segments) targets exactly this remaining cost.

Note: the profile is dominated by basic_amplified because the rich cases are now
sub-4ms. One legitimate net.ParseIP per IP remains (at target creation, to fill
ipU32, and one in the reachable filter); threading uint32 all the way through the
predicate/filter is a documented optional follow-up, deferred because it risks
changing non-IPv4 handling for marginal gain.

Verification: make verify exit 0 (coverage 85.5%).
